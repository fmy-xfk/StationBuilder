# MTR 排图工具（游戏内）

StationBuilder 现在包含一个**独立的列车运行图 / 站台占用分析子系统**。它通过服务端的 MTR
游戏内数据（MTR 的 `list_data` 只读操作）读取线路、车站、站台、车厂和发车数据，在 Minecraft
原生界面里绘制站台占用图、检查站台冲突、给出车厂偏移建议，并把可行的车厂偏移直接写入 MTR
车厂的真实时间时刻表、保存并刷新线路。

> **写入范围**：读取使用 MTR 的只读 `list_data` 操作；只有点击「写入存档」时才会修改车厂的
> 真实时间时刻表并保存/刷新线路，其他 MTR 数据不会被修改。

排图核心不依赖任何 MTR Java 类：数据由服务端通过 MTR 的只读操作读取，因此客户端本身不需要
安装 MTR，只要联机的服务器安装了即可。

## 1. 入口

- 创造模式物品栏：`Auto Station Builder` 物品组中的 **MTR 排图工具**（`stationbuilder:mtr_scheduler`）。
- 手持该物品**右键**即可打开界面；首次打开会先显示一页范围说明（只检查站台占用、不检查进路冲突、
  只分析站台占用），可勾选「本次游戏会话不再显示」后继续。界面只在点击写入时发送偏移写入请求。

## 2. 数据来源

排图数据现在**直接从游戏内的 MTR 读取**，不再访问 MTR 的网页 HTTP API：

1. 客户端在打开排图器 / 点击「刷新」时发送一个 C2S 请求；
2. 服务端在服务器线程上调用 MTR 的 `list_data` 操作（`MTR.sendMessageC2S`），读取当前维度的
   车站、站台、线路、车厂和 Siding 数据；
3. 服务端把数据转换为紧凑 JSON，gzip 压缩后按 30 KB 分块通过自定义 S2C 网络包发送；
4. 客户端在客户端线程重组、解压，并交给排图核心解析。

这样做的好处：

- 多人服务器不需要暴露 MTR 的网页端口，也不要求玩家浏览器访问 `localhost`；
- 客户端不需要安装 MTR，只要服务端安装了；
- 读取在服务端线程完成，避免跨线程访问 MTR 的模拟数据。

不同 MTR 版本的发车接口由版本层适配：1.20.x 使用 MTR 4.0 的 `Siding.getDepartures`，1.21.x
使用 MTR 4.1 的 `Siding.getDeparturesForMap`。若服务端没有安装 MTR，或请求超时（15 秒），界面
会显示错误状态；若该维度没有任何线路，则显示空状态提示而不是错误。

车辆段若勾选了「永久重复车辆指令」（MTR 的 `Depot.repeatInfinitely`），MTR 会为该车辆段生成大量
同一时刻附近的重复车次，直接读取会出现 headway 为 0、重复数十万级的问题。工具会：

- 跳过该车辆段的所有 Siding，不生成这些重复车次；
- 在受影响的线路行显示 `!`，并在线路详情中提示该车辆段及「车次已忽略」；
- 若线路同时还使用正常车辆段，则保留正常车辆段的发车时刻。

## 3. 界面说明

顶部：数据源标识（MTR 游戏内数据）、刷新、关闭。

四个标签页：

1. **线路**：左侧线路列表（含班次数）。右侧显示车厂、衔接关系、首班/间隔/班次输入框和当前
   车次的逐站时刻表（到达 / 发车）；站序较多时可用鼠标滚轮、`^`/`v` 或 `PgUp`/`PgDn` 滚动（`Home`/`End`
   跳到首尾），不再截断站点。`间隔` 取所有发车间隔的中位数，避免首段不规则间隔造成误读。
   - `生成`：按「首班 + 间隔 × 班次」重建该线路的发车时刻（仅本工具）。
   - `-5m / -1m / +1m / +5m`：整体平移该线路。
   - `衔接`：在左侧列表中选择一条前序线路，本线路发车时刻改为前序线路的**末站到达时刻**。
     只有当前序线路的末站与本线路首站位于**同一车站、同一站台**时才允许衔接（与网页版语义
     一致）；首站占用会被去重，避免同一列车被重复计算。
   - 载入数据时会自动检测「同一车站同一站台、且共用同一车厂」的顺次线路，并标记为
     `衔接自 …（自动）`。自动衔接**只去除折返站的重复占用**，不会改写 MTR 报告的发车时刻；
     判断方向时会选择「末班到达 → 首班发车」折返时间最短且不超过 2 小时的一侧，避免反向误判。
     手动点击 `衔接` 才会按前序线路的到达时刻重排本线路。`清除` 后本次游戏会话内不再自动恢复。
   - `清除`：移除衔接关系（不恢复时刻）。
2. **站台占用**：左侧车站列表。右侧为时间范围（默认 **06:00-07:00**，可编辑、`Now`、`±1h`）与站台占用
   甘特图，一行一个站台，颜色取线路颜色，悬停显示线路与占用区间。
3. **冲突**：当前时间范围内的站台重叠 / 间隔不足列表。列表按「车站 + 站台 + 线路对」聚合，
   每行显示发生次数与最差间隔，悬停可看完整时间范围；不会为每一趟车重复列一行。下方附带差分
   约束求出的**建议车厂偏移**与 `应用偏移`。点击冲突行会跳转到对应车站的占用图。

## 4. 排图模型

- 每条线路保存有序站台（`dwellMs`）和区间运行时分（`durationsMs`），由发车时刻推出逐站
  到达/发车时间轴；时间轴使用**绝对毫秒**，仅在显示时按 24 小时取模，因此 23:58 到达、
  00:04 离开的停站不会被误判。
- 分析窗口内按「车站 + 站台」分组，排序后检查相邻占用：
  - 重叠 → 错误；
  - 间隔 < 60 秒 → 警告。
- 对相邻占用 `前车离开 end` 与 `后车到达 start` 建立差分约束：

  ```text
  (end_prev + o_prev) + gap <= start_cur + o_cur
  => o_prev - o_cur <= start_cur - end_prev - gap
  ```

  变量是各车厂的偏移量 `o`。Bellman–Ford 判断可行性并求最短距离；解出的距离无法确定整体
  平移量，因此固定**出现次数最多的车厂为参考车厂（偏移 0）**，其余车厂取相对偏移，
  避免网页版「所有车厂一起提前」的问题。
- 最大间隔用倍增 + 二分搜索求解，搜索上限 10 分钟；达到上限时结果标记为「至少」，
  而不是像网页版那样固定上限 300 秒。**实际应用偏移时以 60 秒安全间隔为目标**求解，
  避免为了追求更大的理论间隔而产生不必要的整体平移；最大间隔只作为信息展示。
- MTR 的 `departures` 数据是「线路终点发车」：普通情况下取末站发车减去全程运行时间得到首站
  发车；当车厂把两条线路串在同一站台折返时，MTR 会改为上报后一线路的首站发车，此时只减去首站
  停站时间。工具会根据衔接关系和双向折返关系自动选择解释方式，减少首班/间隔偏差；环线数据中多出的闭合运行区间
  不计入首站推算。
- 同一车厂的两条线路互相冲突时，整体平移无法改变相对间隔，这类冲突单独计数并提示。
- 折返站按「同一车站 + 同一站台 + 共用同一车厂 + 折返时间不超过 2 小时」识别为顺次线路并自动
  去重；这是几何 + 时刻启发式，如果同一站台确实由两条独立线路使用，可在「线路」页点 `清除`
  取消自动衔接。

## 5. 写入 MTR

「写入存档」会把当前建议的车厂偏移加到 MTR 车厂已有的**真实时间时刻表**上，然后：

1. 调用 MTR 的 `Simulator.save()` 保存偏移后的时刻表；
2. 调用 `Depot.generateDepots(...)` 重新生成受影响车厂的线路和车次；
3. 再次保存，并把刷新后的 `list_data` 快照发回客户端。

限制：

- 车厂必须已经启用「真实时间」且有非空时刻表；频率模式会报错，不会覆盖原配置；
- 勾选「永久重复车辆指令」的车厂会被跳过，避免重复车次问题；
- 只移动整个车厂，因此同一车厂内部两列车之间的相对间隔不会改变。

## 6. 代码结构

纯 Java 排图核心（不依赖 Minecraft / MTR，可在游戏外单独编译测试）：

```text
common/src/main/java/cn/myfrank/stationbuilder/scheduler/
├─ Json.java               极小 JSON 读写器（不依赖 Gson）
├─ TimeFormat.java         运营日时间与 HH:MM:SS 解析/格式化
├─ MtrStation.java         车站快照
├─ MtrStop.java            线路站台停站
├─ StopTime.java           到达/发车对
├─ MtrRoute.java           线路、区间运行时分、时间轴
├─ MtrNetwork.java         网络快照解析
├─ SchedulerAnalysis.java  站台占用、冲突、差分约束与车厂偏移
├─ SchedulerSession.java   客户端会话状态（加载、编辑、衔接、偏移）
└─ client/MtrSchedulerClient.java  客户端打开界面入口
```

服务端数据适配与网络（按加载器/版本放置）：

```text
1.20-common/…/mtr/MtrGameDataSource.java   MTR 4.0 list_data → JSON
1.21-common/…/mtr/MtrGameDataSource.java   MTR 4.1 list_data → JSON
…/mtr/MtrEmptyRequest.java                 list_data 空请求体
…/mtr/MtrSchedulerNetworking.java          请求/分块数据包/写入请求
…/mtr/MtrSchedulerClientTransport.java     客户端请求、重组与解压
common/…/mtr/MtrDepotOffsetWriter.java     写入真实时间时刻表并刷新车厂
```

界面：`common/src/main/java/cn/myfrank/stationbuilder/screens/MtrSchedulerScreen.java`
（只使用 `Screen` / `DrawContext`(或 `GuiGraphics`) / `TextRenderer`(或 `Font`) 等跨版本稳定 API）。

物品与注册：

- `1.20-common` / `1.21-common` 的 `items/MtrSchedulerItem*.java`；
- `ModItems` 注册 `mtr_scheduler`，并加入 StationBuilder 创造模式物品组；
- `1.21.x` 额外提供 `assets/stationbuilder/items/mtr_scheduler.json` 物品模型定义。

## 7. 构建与自测

```bash
# 在对应目标目录中
gradlew.bat build        # Windows
./gradlew build          # Linux / macOS
```

编译已验证的 8 个目标：Fabric 1.20.1 / 1.20.4 / 1.21.1 / 1.21.4，Forge 1.20.1 / 1.20.4，
NeoForge 1.21.1 / 1.21.4。

排图核心可以脱离游戏测试：

```bash
javac --release 17 -d out common/src/main/java/cn/myfrank/stationbuilder/scheduler/*.java
# 再编译并运行任意调用 scheduler 包的测试程序
```

## 8. 已知限制

- **只分析站台占用**：不覆盖区间闭塞、道岔、单线会车、追踪间隔；界面中的「无冲突」只代表
  当前窗口内站台占用未发现问题。
- **每个线路只使用第一个车厂**作为可调变量；一条线路挂多个车厂时不会拆分车底。
- **不做车底循环 / 折返能力 / 备用车约束**，衔接关系只是时刻推导。
- **只支持真实时间车厂**：频率模式车厂需要先在 MTR 中切换为真实时间时刻表，否则写入会报错。
- **只写车厂偏移**：写入不会重建每条线路的独立时刻表，只平移车厂现有真实时间时刻表。
- 发车数据来自 MTR「即将发车」列表，时间范围之外的车次需要手动补录；首班/间隔仍是从该列表推算的
  估计值，短交路、多车厂或特殊车厂串行方式可能与游戏内排图略有差异。
- **服务端要求**：数据由服务端读取，因此服务端必须安装 MTR；客户端可以不安装。若服务端没有
  MTR，或 MTR 尚未初始化完成，界面会显示错误而不是卡住（15 秒超时）。
